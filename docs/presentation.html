Procurement Agent

A supervisor-orchestrated agent system that sources industrial parts across two search engines and returns what they actually cost delivered to Tashkent.

The problem

One person, seven jobs, for every single part

A colleague of mine sources industrial sensors. He is handed a part number and has to come back with a price, a lead time and a recommendation he can defend. Between those two moments sits all of this — and none of it is judgement.

Find who sells it

Search in two languages, open thirty tabs, most of them dead ends.

Check the specs

Read a datasheet PDF to confirm it is actually the right part.

Compare the prices

Different currencies, different quantities, different shipping terms.

Add the customs

Duty and VAT, by hand, on every option separately.

Email the rest

Half the suppliers publish no price at all. Write, wait, chase.

Remember last time

What did we pay, from whom, and did they actually deliver on time?

Do it again

Next month, next part, from the beginning.

Under deadline

Steps get skipped. Usually the customs maths, because it is the dullest.

Hours per part, and it is all mechanical. That is the problem — not the arithmetic, the volume of it landing on one person.

The five specialists

Each answers a different kind of question

Scout

Queries Google and Baidu through SerpApi, ranks results by a per-source weight, then reads pages down a three-rung ladder.

who sells it, at what price

Part

Similarity search over datasheets in Qdrant. Spec tables that exist only as images are captioned by the vision model first.

signals, voltage, IP rating

History

The model writes one SELECT against a documented schema, run read-only with three independent guards.

what we paid before

Analyst

Executes the costing model in Python — currency, incoterm, freight mode, duty, VAT. The model never does arithmetic.

landed cost, sensitivity

RFQ

Drafts a supplier email for anyone publishing no price, and parses the reply back into the same offer schema.

prices that live in inboxes

Plus two that decide rather than gather: the Supervisor chooses who runs next, and the Critic verifies the answer before anyone sees it.

05Procurement Agent

How routing actually works

The model decides. Code dispatches.

It never runs anything and never jumps anywhere. It writes one word into shared state. Plain Python reads that word and calls the function.

Its only power over control flow is the value it writes.

1  The model

Reads the question and what has been gathered. Emits one token under a JSON schema — five valid values, so the parse cannot fail.

"analyst"

2  Plain Python

A routing function reads that field and returns a node name. No model involved at this step at all.

return state["plan"]

3  The function runs

LangGraph dispatches to that node. Its result goes back into state, and the supervisor is asked again.

evidence appended

Getting the data

Three ways to read a page, and one honest refusal

1  Direct fetch

httpx with a real user agent, HTML flattened by BeautifulSoup, truncated to 12k characters before extraction.

manufacturers, Made-in-China

2  Headless browser

Playwright Chromium, images and fonts blocked, one browser reused across the batch. Recovered a page returning 403.

JavaScript pages, robu.in

3  Ask a human

Alibaba serves a slider CAPTCHA. We do not attempt it. Paste the page, or send the supplier an RFQ.

CAPTCHA-walled sources

Failure falls through, it never guesses. Every row in the table records which rung produced it, so a scraped listing is never mistaken for a quote addressed to us.

Reading six pages used to take 40 seconds

Each page was fetched, then extracted, one after another — and a fresh browser was launched for every page that needed one.

Now the pages are read at the same time, one browser is shared, and extraction stops as soon as enough priced offers exist.

The insight

The right supplier depends on how many you buy

At one unit the local supplier wins — minimum shipping charges swamp everything. At fifty, the Chinese quote wins by eleven dollars a unit.

Nobody checks this by hand. It is an hour in a spreadsheet, so it does not get done.

Traps, not just targets

One case requires IP68, which exists only inside an image caption — passing it proves the vision path works. Another forbids "cheapest is $40", the answer you get if you fail to convert CNY.

11Procurement Agent

What went wrong

Three bugs, one shape

It invented a fact

Told "bought 56 at $41 each", it recorded the price as delivered, all in. Nobody said that. $41 at the factory gate is about $60 delivered.

fix: code blanks the field

It skipped a question

"Find me FST100-2006A" was marked ready to search with no quantity — the one field that moves MOQ, tier pricing and freight mode.

fix: the question is injected

It compared two currencies

Given 260 CNY and $40 USD, it answered $40 was cheaper. CNY 260 is $38.67.

fix: convert first, then show

All three passed a test before we found them. Nothing crashed. Each produced a confident, plausible, wrong answer — which is the failure mode that matters with this technology.

An instruction is a suggestion.
A check in code is a guarantee.

12Procurement Agent

Guardrails

Two places the model could do damage

The SQL agent writes its own queries

Three independent layers, because one is not enough when a model writes the statement:

• The generated SQL must start with SELECT or WITH
• A keyword scan rejects any write verb, and stacked statements
• The connection runs under PRAGMA query_only

DELETE, stacked DROP and UPDATE all blocked in testing

The RFQ agent emails real suppliers

The only irreversible action in the system, so it is gated in code rather than by convention:

• One function can send, and it refuses any draft not marked approved
• dry_run defaults to true on every call
• A person reads the text before it goes

unapproved send returns 403
POST /rfq/1/send      403  "rfq #1 is 'drafted', not 'approved'."
POST /rfq/1/approve   200  {"status": "approved"}
POST /rfq/1/send      200  {"sent": true}

14Procurement Agent

Limitations

What this version does not do yet

Customs rates are unverified

The duty table is deliberately empty. Every costing prints "20 %, unverified" rather than inventing a rate. Filling it needs the official tariff.

The browser rung is local only

Headless Chromium needs 1–2 GB of RAM. The free host gives 512 MB, so it cannot launch there. Deployed, the ladder is direct fetch, then manual paste or an RFQ.

No distributed tracing

Agent steps are visible in the live trace and in phase timings, but there is no trace store, so cost and token accounting per run is not captured.

Email sending is unproven

Drafting, approval and refusal are all tested. Actually sending has never run against a real mailbox.

Spec names are not normalised

output_signal and signal_output compare as two different parameters. Harmless so far, but it clutters equivalence checks.

Inventing plausible customs rates would have been easy and looked better. It is also the exact mistake this project exists to prevent, so the number stays marked unverified.

What is next

Three concrete steps

01  Trace store

Wire Langfuse so every run records its routing decisions, token counts and cost, and regressions become visible instead of anecdotal.

02  Prove the email loop

Run the RFQ path against a real mailbox end to end — send, receive, parse the reply into an offer, and let a real quote enter the table.

03  Widen the evaluation

Twenty cases and single runs are enough to sanity-check, not enough to claim a rate. More cases, repeated runs, variance reported.
