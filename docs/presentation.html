The problem

The price on the page is not the price you pay

A colleague of mine sources sensors and industrial components. He is handed a part number and has to come back with a price, a lead time, and a recommendation he can defend.

He opens thirty tabs. Prices in different currencies, at different quantities, under different shipping terms. Then he does the customs maths in his head, or does not do it at all.

$45 → $68.55

A 52 % gap between the sticker price and the real one. and it is different for every supplier

How it works · orchestration

Five specialists, one manager, one inspector

How it works · the mechanism

The AI decides. Code orchestrates.

This is the part people assume is magic. It is not.

The model never runs anything and never jumps anywhere. It writes a single word into shared memory. Ordinary Python reads that word and calls the matching function.

Its only power over what happens next is the value it writes.

How it works · getting the data

Some doors do not open

Alibaba answers with a CAPTCHA. We could have spent weeks fighting it, and lost the fight every time they changed it.

So the system degrades on purpose: when a page cannot be read, it says so and offers the two things that still work — paste it in yourself, or email the supplier.

Nothing silently returns a wrong price.

Results · the insight

The right answer depends on how many you buy

At one unit, the local supplier wins — minimum shipping charges swamp everything else.

At fifty, the Chinese quote wins by eleven dollars a unit.

Nobody checks this by hand. It takes an hour in a spreadsheet, so it does not get done, and the wrong supplier gets the order.

Problems we hit · 1 of 3

The model quietly invented a fact

what broke Told “bought 56 sensors at $41 each”, it recorded the price as delivered, all costs included. Nobody said that.
why $41 at the factory gate becomes about $60 delivered. The instruction said “never assume”. It assumed anyway.
what we did Stopped trusting the instruction. A few lines of code now blank that field unless the user's own words contain a shipping term.
result It asks instead of guessing — and every future comparison against that purchase stays honest.
An instruction is a suggestion. A check in code is a guarantee. we found three more of these the same way

Problems we hit · 2 of 3

A bigger model was the obvious fix. It changed nothing.

what broke Asked “what is the landed cost?”, the manager sent the question to the datasheet reader. Wrong specialist.
the obvious fix Use a stronger, more expensive model. We tried it. Identical score, identical failure.
the real cause We had never told it that costing needs prices first. It reasoned “understand the part before pricing it” — sensible in general, wrong here.
result Two sentences of explanation. Perfect routing on the cheap model.
We measured before we spent. The upgrade would have cost money and fixed nothing.

Problems we hit · 3 of 3

It compared two currencies and got it backwards

what broke Asked for the cheapest listed price, it saw 260 CNY and $40 USD and answered $40. CNY 260 is $38.67.
why We handed it two numbers in different units and expected it to do the conversion in its head. It cannot, reliably.
what we did Convert in code first, then hand it a finished comparison. It reads an answer instead of calculating one.
result Correct every time — and the inspector agent, which had been rejecting these, now passes them.

All three bugs passed a test before we found them. None crashed. They produced confident, plausible, wrong answers — which is the failure mode that matters with this technology.

One design decision worth defending

The agent never sends an email on its own

It drafts. A person approves. Only then does anything leave the machine.

This is not a setting. There is no flag that overrides it, and only one function in the codebase can send at all — it refuses any draft that has not been approved.

Emailing a real supplier under someone's name is the only thing here that cannot be undone.

# asking it to send an unapproved draft
POST /rfq/1/send
403  "rfq #1 is 'drafted', not 'approved'."

# a person reviews the text and approves
POST /rfq/1/approve
200  {"status": "approved"}

# now it will send
POST /rfq/1/send
200  {"sent": true}

the same gate protects the follow-up chasers

What is not done

Three things I would fix first

customs rates

The duty table is deliberately empty. Every calculation says “20 %, unverified” rather than inventing a rate. Filling it needs the official tariff document.

spec naming

output_signal and signal_output are treated as two different things. Harmless so far, but it clutters the comparison.

email sending

Drafting, approval and refusal are all tested. Actually sending is written but has not been run against a real mailbox.

Inventing plausible customs rates would have been easy and would have looked better. It is also exactly the mistake this whole project exists to prevent, so the number stays marked unverified until someone checks it.

What I learned

Three things I did not know before this

  • Orchestration is not magic. The model writes a word; ordinary code reads it and calls a function. Once that clicked, the whole system became debuggable.
  • Measure before you upgrade. The obvious fix for a weak decision was a stronger model. It scored identically. The problem was something I had failed to explain.
  • The dangerous failures are the quiet ones. Nothing crashed. Every bug we found produced a confident, reasonable-looking, wrong answer.

And one that is not technical: I built this for a specific person doing a specific job. Every time I guessed what he needed instead of asking, I built the wrong thing.
